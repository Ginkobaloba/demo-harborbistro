# 2026-09-19 16:09 CDT - Sign the hb_visitor cookie (D-018)
- **Who:** Claude Opus 5 (1M context), tier-3 fix dispatched by the Orchestrator.
- **Change:** `hb_visitor` is now `<uuid>.<base64url HMAC-SHA-256 tag>` under a key derived from `SESSION_SECRET` with the label `harborbistro:visitor-cookie:v1` (same design as demo-slatewell D-016). Untrusted cookies read as no visitor; the middleware and both write routes mint a fresh signed visitor instead of adopting a claimed id. The database keeps the bare id. `SESSION_SECRET` is read in one place (`src/lib/session-secret.ts`) for both the visitor key and the portal session.
- **Why:** the unsigned id was a bearer token for another visitor's scope. Hard call: with no usable `SESSION_SECRET`, reservations and checkout answer 503 and no cookie is issued (fail closed, like D-015 and D-016), rather than falling back to a random per-process key, which would hide the misconfiguration and log everyone out on every restart.
- **State after:** every pre-D-018 cookie becomes a new visitor on the next page view (accepted: visitor data expires in about a day). Deploy gate: production must set a 32+ character `SESSION_SECRET` before this ships, or both write paths 503 (whether prod has one today is unverified). Not merged; awaiting an independent deep verify.
- **Refs:** docs/decisions.md D-018, src/lib/visitor.ts, src/lib/session-secret.ts, src/middleware.ts, test/server/visitor-cookie.server.test.ts.
